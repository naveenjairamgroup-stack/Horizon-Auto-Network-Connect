# Horizon Auto — Network Connect

Dealer network ERP for Horizon Auto (Honda two-wheeler dealer network,
Jharkhand). Tracks vehicle sales, parts supply, commission, outstanding,
credit limit, and inventory value across AD / ASC / FO dealer types.

## Architecture

```
┌─────────────┐   same-origin   ┌───────────────────────┐   server-to-server   ┌───────────────────────┐
│  Browser     │ ──────────────▶ │  Cloudflare Pages      │ ───────────────────▶ │  Google Apps Script    │
│  (frontend/) │ ◀────────────── │  Function (/api)       │ ◀─────────────────── │  Web App API           │
└─────────────┘    JSON          │  frontend/functions/    │      JSON            │  Data: Google Sheets    │
                                  └───────────────────────┘                       └───────────────────────┘
```

- **Frontend** is a static single-page app — no build step, no framework,
  just ES modules loaded directly by the browser. Deployed automatically by
  Cloudflare Pages whenever this repo's `frontend/` folder changes.
- **The `/api` proxy** (`frontend/functions/api.js`) is a Cloudflare Pages
  Function — it exists solely because this Apps Script deployment (a Google
  Workspace domain-restricted project) doesn't reliably send CORS headers a
  browser can act on, on GET, POST, or JSONP. A server-to-server call isn't
  subject to browser CORS at all, so the browser talks to its own domain
  and the Function relays to Apps Script behind the scenes. See
  `docs/DEPLOYMENT_GUIDE.md` §"Why a proxy?" for the full story.
- **Backend** business logic is unchanged from before — every function is
  exactly what it always was, wrapped in `safeRun()` the same way. Only the
  transport in front of it (`backend/Code.gs`'s `API_DISPATCH`) is new.
- **Database** is still the same Google Sheet; nothing about the data model
  changed.

## Folder structure

```
frontend/
  index.html            ← generated by build.py from pages/*.html — this is what Cloudflare Pages serves
  build.py               ← local dev convenience: regenerates index.html after you edit a page fragment
  functions/
    api.js                ← Cloudflare Pages Function: proxies /api to Apps Script (reads APPS_SCRIPT_URL env var)
  pages/                 ← one HTML fragment per screen (source of truth)
  assets/
    css/styles.css
    js/
      api.js             ← calls same-origin /api (no backend URL on the client at all)
      session.js          ← shared login/session state
      router.js           ← page show/hide + role→dashboard mapping
      sidebar.js           ← builds the left nav per role
      auth.js              ← login / logout

      pages/                ← one module per screen, mirrors pages/*.html

  Utils/ Auth/ Audit/ Masters/ Ledger/ Payments/ Returns/

  .clasp.json            ← put your Apps Script project's Script ID here

```

## Quick start (after cloning)

1. **Backend**: see `docs/DEPLOYMENT_GUIDE.md` §Part 1 — push via `clasp`, deploy as a Web App, copy the plain `/exec` URL.
2. **Proxy**: in Cloudflare Pages project settings, set environment variable `APPS_SCRIPT_URL` to that URL, then redeploy (§Part 2.2).
3. If you edited anything under `frontend/pages/`, run `python3 frontend/build.py` to regenerate `index.html`.
4. Commit and push — Cloudflare Pages picks it up automatically.

## Adding a new backend function

1. Write the function anywhere under `backend/` as usual (it should call `safeRun(...)` like every existing function does).
2. Add it to the `API_DISPATCH` object in `backend/Code.gs` — this is both the router and the security whitelist; anything not listed there cannot be called from the frontend.
3. Call it from the frontend the same way as everything else: `api('yourFunctionName', session.token, ...)`.

## Performance notes

Two real inefficiencies were found and fixed (not every generic "make it
faster" suggestion holds up at this system's actual scale — a few dozen
dealers, low thousands of ledger rows — but these two were genuine):

- **`getAllRows()` now caches per-request.** Apps Script gives each web
  request its own fresh execution context, so a plain in-memory cache is
  safe: it starts empty every request and is shared by every function
  called during that one request. Before this, something like the Stock
  import's per-vehicle price lookup (`lookupExShowroomPrice_`) re-read the
  *entire* `All_Model_Price_List` sheet once per vehicle — 300+ full-sheet
  reads for a 300-vehicle stock file. Now it's read once and reused.
- **Bulk inserts use `appendRows()` (one `setValues()` call) instead of one
  `appendRow()` per row.** The Stock import's per-vehicle detail rows were
  the worst offender — up to 300+ individual Sheets API calls in a single
  import, now a single batched write. `appendRow()` (singular) still exists
  for the many call sites inserting one row at a time (a payment, a return,
  a single ledger entry) — batching only matters where a loop inserts many
  rows in one go.

Not changed, on purpose: the several places that still call `appendRow()`
per invoice line during Vehicle Sale / Parts Sale import. Those loops run
over a handful of frames or line items *per invoice*, not hundreds in one
shot — batching them would add code complexity for a difference too small
to measure at this system's actual data volumes.
